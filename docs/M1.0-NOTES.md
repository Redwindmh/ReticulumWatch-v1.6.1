# M1.0.1 notes — Opportunistic LXMF inbox foundation

## Goal

Prove the first complete messaging vertical slice on the T-Watch S3 without
pulling in a large desktop-style LXMRouter implementation.

M1.0.1 accepts **opportunistic** LXMF deliveries on an on-device
`lxmf.delivery` destination, decodes the current LXMF payload, persists the
message and notifies the user.

## Architecture

```text
Python LXMF / Sideband-compatible sender
              |
         Reticulum packet
              |
            LoRa
              |
          SX1262
              |
     RNode framing/reassembly
              |
       microReticulum
              |
       lxmf.delivery
              |
        LxmfService queue
              |
     MessagePack decode
              |
        StorageService
              |
     /lxmf/inbox/*.lxm
              |
       haptic + LVGL
```

The Reticulum destination packet callback only copies the decrypted delivery
payload into a fixed four-entry queue. MessagePack parsing, FFat writes and
haptic/UI work happen later from the normal firmware loop.

## Wire format targeted

M1.0.1 targets the current LXMF opportunistic delivery form:

```text
source_hash (16)
signature   (64)
msgpack payload
```

The destination hash is implicit in the Reticulum destination receiving the
opportunistic packet.

The MessagePack payload is decoded as:

```text
[timestamp(float64), title(bin), content(bin), fields(map), optional_stamp?]
```

M1.0.1 reads the first four structural positions needed for the inbox and ignores
fields/stamp content for now.

## Persistence

StorageService creates:

```text
/reticulum
  /lxmf
    message_count.bin
    /inbox
      00000001.lxm
      00000002.lxm
      ...
```

Each fixed-version record stores:

- sequence
- timestamp
- 16-byte source LXMF destination hash
- 32-byte derived LXMF message id
- source-known flag
- signature-verified flag
- bounded title
- bounded content

The latest record is restored on boot.

## Protocol TX behavior changes from M0.5

M0.5 intentionally kept `_OUT=false` except around the first controlled
announce. That is no longer appropriate once the watch is a messaging endpoint:
Reticulum needs to emit ordinary protocol traffic such as delivery proofs.

M1.0.1 therefore runs the SX1262 interface with:

```text
_IN  = true
_OUT = true
```

Application announces remain explicitly user-triggered, but protocol responses
are no longer artificially blocked.

## Security boundary

Received LXMF signatures are not marked trusted in M1.0.1.

The stable firmware baseline is still microReticulum 0.5.0. A later-discovered
`Identity::validate()` bug in the microReticulum family ignored the Ed25519
verification result, so M1.0.1 does not use that API to claim authenticity.

M1.0.1 stores and shows all successfully decrypted/decoded messages as
`UNVERIFIED`. Before contacts, trusted sender names, replies or security-sensitive
actions are enabled, move to a known fixed microReticulum revision and add
cross-implementation signature test vectors.

## Acceptance criteria

1. Firmware builds and boots without changing the persistent Reticulum identity.
2. `lxmf.delivery` destination is created and printed.
3. **ANNOUNCE LXMF** makes the peer learn a one-hop path.
4. Python LXMF `OPPORTUNISTIC` message reaches the destination callback.
5. Current MessagePack title/content decode correctly.
6. Message is persisted under `/lxmf/inbox`.
7. Watch vibrates once and displays the latest message.
8. Reboot restores message count and latest message.
9. Reticulum protocol remains able to transmit delivery proofs.
10. `--long` test exercises RNode split RX/reassembly if the resulting Reticulum
    packet exceeds one physical LoRa frame.

## Deferred

- authenticated LXMF signature verification
- stamp validation/tickets
- Direct delivery over Reticulum Link
- Resource-backed larger messages
- outbound LXMF composing/sending
- contacts/conversations
- full inbox list
- keyboard and quick replies
