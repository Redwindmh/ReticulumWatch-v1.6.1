# M1.4.0 — LXMF security rebase and validation gate

## Milestone purpose

The master build plan requires ReticulumWatch to stop relying on the pinned microReticulum lineage with the known `Identity::validate()` failure before presenting remote messages as cryptographically verified.

M1.4.0 is the controlled first security-hardening build. It changes the dependency/security boundary while keeping the proven radio profile, application identity location, LXMF history model and M1.3 outbound behavior intact.

## Changes

### microReticulum dependency

- Replaced RatSpeak commit `290a1336ebe05782c80a1debf8a8da0316a88ae7` with `attermann/microReticulum @ 0.5.0`.
- Replaced individual legacy public headers with `<microReticulum.h>`.
- Updated `WatchLoRaInterface::send_outgoing()` to the modern `bool` virtual signature.
- Replaced the old RNS-native filesystem shim with `microStore::Adapters::NoopFileSystem`.
- Kept RNS internal persistence and provisioning disabled to avoid mixing a security rebase with an application-storage redesign.

### Cryptographic fail-closed self-test

Before exposing the LXMF destination, boot creates an ephemeral test identity and checks the exact linked `Identity::validate()` implementation:

1. sign a fixed message;
2. valid signature must validate;
3. one-bit-tampered signature must reject;
4. one-bit-tampered message with the original signature must reject.

The endpoint stays disabled if any condition fails.

Expected line:

```text
[security] Identity::validate self-test: valid=PASS tampered-signature=REJECT tampered-message=REJECT => PASS
```

### Trust state

Incoming message history now carries one of four explicit states:

- `UNKNOWN` — source identity unavailable;
- `KNOWN` — source identity available, but no trustworthy verification claim;
- `VERIFIED` — current M1.4 runtime validated the signature;
- `FAILED` — current M1.4 runtime had the source identity and rejected the signature.

LMX3 keeps its existing packed size and CRC. The state is stored in previously reserved bytes with a marker. Historical incoming records without that marker are deliberately downgraded to `KNOWN`/`UNKNOWN`; their old `signatureVerified` flag is not trusted.

## Deferred issue

The DRV2605 initializes, but M1.3.2/M1.3.3 button haptics remained too weak to be useful on hardware. The user chose to defer this rather than block protocol progress. Keep that issue open for later M2/M3 interaction/hardware tuning.

## Acceptance

Do not erase the Reticulum partition.

1. Force a clean dependency resolution and build M1.4.0.
2. Boot and require the signature self-test PASS line.
3. Confirm the application identity is unchanged.
4. Confirm older incoming history is not automatically shown as VERIFIED.
5. Receive a fresh correctly signed message from a known peer; require `VERIFIED`.
6. Send/receive over an active Link.
7. Reboot and independently send with SEND MORE so the M1.3 path-request/opportunistic route is re-proven.
8. Keep outbound state at `SUBMITTED` unless genuine remote delivery validation is implemented.
9. Prefer an externally crafted intentionally invalid signature test before closing all of M1.4, even though the boot self-test already exercises the negative validation path in the linked runtime.
