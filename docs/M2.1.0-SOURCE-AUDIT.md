# M2.1.0 source audit

## Scope boundary

M2.1.0 intentionally changes inbox/UI-state persistence and presentation only. It does **not** intentionally change:

- `src/radio/RadioService.*`;
- `src/reticulum/WatchLoRaInterface.*`;
- the SX1262 profile;
- RNode-compatible framing/split handling;
- partition maps;
- microReticulum or microStore version pins;
- identity/destination construction;
- LXMF wire encoding or send routing.

`LxmfService.cpp` changes only the milestone boot string and the announce diagnostic wording. It does not claim that peer acceptance follows from local announce emission.

## Persistent unread model

The unread marker namespace is `/lxmf/metadata/unread`. It is intentionally separate from the CRC-protected history files. The boot audit removes markers that do not resolve to a readable incoming message. Retention removes markers at or below the same history cutoff.

Legacy history has no unread marker and therefore loads as read. New outgoing messages are always read. New incoming messages become unread only after their authoritative history record has been committed.

## Delivery-state honesty

The existing `LxmfDeliveryState::Submitted` semantics remain unchanged. M2.1 merely makes this visible in the UI and explicitly states that `SUBMITTED` is not a remote delivery proof.

## Announce compatibility

The attached M1.4.4 hardware log showed two 187-byte Reticulum announce packets and 188-byte PHY frames transmitting successfully, while the receiving application did not surface the watch announce. This establishes a peer-acceptance/interoperability problem above the raw SX1262 transmit result; it does not by itself establish the exact encoder defect.

The reference Python Reticulum implementation includes a five-byte timestamp in the lower half of the announce freshness blob. A future announce repair must compare the exact pinned microReticulum 0.5.0 bytes/signature input against that reference and must be validated by a receiving Python Reticulum/LXMF client.
