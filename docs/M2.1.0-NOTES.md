# M2.1.0 — Inbox

M2.1.0 starts the Messenger User Experience milestone on top of the hardware-proven M1.4.4 messaging baseline.

## Hardware evidence carried forward

The M1.4.4 hardware log showed:

- microReticulum 0.5.0 starts successfully with the no-op microStore adapter;
- the signature self-test accepts the valid case and rejects tampered signature/message cases;
- two watch-originated `lxmf.delivery` announce packets were handed to the SX1262 successfully, but the peer did not surface those announces;
- an incoming Reticulum Link was established;
- an incoming LXMF message was received and persisted;
- a signed watch reply was submitted over the Link and the radio transmission completed successfully.

The log does not contain a radio-layer error for the user-observed single failed transmission. M2.1 therefore keeps the working radio path frozen and continues to represent local sends as `SUBMITTED` unless a trustworthy remote proof is available.

## Inbox changes

M2.1.0 adds:

- persistent unread/read state for newly received messages;
- unread count in the inbox header/footer;
- `*` unread marker on incoming inbox rows;
- sender/destination short hash on every row;
- UTC message time on inbox rows and UTC date/time in message detail;
- newest-first history ordering (preserved from the existing history list);
- mark-as-read when an incoming message is opened;
- explicit outgoing delivery-state presentation; `SUBMITTED` is labelled as having no delivery proof.

Existing pre-M2.1 history defaults to **read**. This avoids making an entire historical inbox appear newly unread after upgrade.

## Persistence design

Unread state is deliberately **derived metadata**, not a rewrite of the CRC-protected LMX3 message record. New incoming messages receive a one-byte marker:

```text
/lxmf/metadata/unread/00000042.unr
```

Opening that message removes the marker. This preserves the existing LMX1/LMX2/LMX3 record formats and avoids rewriting an otherwise valid message just to change UI state. Orphan markers are removed during boot audit, and retention removes unread markers for pruned history.

## Announce regression

The `ANN` control remains available for interoperability testing, but M2.1.0 no longer prints the misleading phrase `interoperable announce sent`. Local success only means an announce packet was emitted into Reticulum/radio; it does not prove that another Reticulum implementation accepted it.

Upstream Reticulum currently creates the 10-byte announce freshness field as five random bytes followed by a five-byte big-endian Unix timestamp. microReticulum 0.5.0 also added replay/out-of-order announce rejection, so announce freshness/ordering is a high-priority compatibility area to compare against the exact pinned C++ encoder before peer discovery work in M2.4. This is tracked as an open interoperability regression, not silently declared fixed.

## Acceptance test

1. Clean-build and flash without erasing the Reticulum partition.
2. Confirm boot restores existing history and reports `unread incoming messages=0` for pre-M2.1 history.
3. Send a new LXMF message to the watch.
4. Confirm the inbox header increments to `INBOX (1)` and the new row begins with `*`.
5. Open the new message; confirm the timestamp is visible.
6. Return to the inbox; confirm the unread count is zero and the row no longer begins with `*`.
7. Restart the watch; confirm the read state remains read.
8. Receive another message and restart **before opening it**; confirm it remains unread after restart.
9. Reply to a message and confirm the remote peer receives it. Open the outgoing history row and confirm it says `SUBMITTED (no delivery proof)` rather than falsely claiming delivery.
10. Optionally tap `ANN` and capture both watch and peer logs; announce acceptance remains a separately tracked regression.
