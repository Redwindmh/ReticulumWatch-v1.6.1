# M1.2.4 — deterministic on-screen restart for persistence acceptance

## Major milestone

Still **M1 — LXMF Messaging Core**, specifically the reboot acceptance work for **M1.2 — Persistent Inbox and Message History**.

This is a patch release, not a new conceptual milestone.

## Why this patch exists

The first M1.2.3 hardware boot successfully migrated and audited the existing message history, but the planned second-boot acceptance test could not be performed because pressing/holding the watch crown did not restart the device.

Inspection of the current ReticulumWatch source showed no explicit crown/button input handler in `WatchHardware`, `PowerManager`, `WatchUI`, or `main.cpp`. Therefore the persistence acceptance test should not depend on undocumented crown behavior.

## Smallest change

M1.2.4 adds an **RST** control to the inbox header.

Flow:

```text
Inbox
  -> RST
Restart confirmation
  -> CANCEL  -> Inbox
  -> RESTART -> WatchHardware::restart() -> ESP.restart()
```

`WatchUI` never directly owns the reset primitive. `WatchHardware` exposes `restart()` so system/hardware ownership remains centralized.

## Untouched known-good behavior

No intentional changes were made to:

- RadioService;
- WatchLoRaInterface;
- ReticulumService;
- LxmfService wire format or send/receive path;
- StorageService record/index layout;
- radio profile;
- composer/keyboard geometry.

## Acceptance

1. Build/flash without erasing `/reticulum`.
2. Confirm old messages and identity remain.
3. Tap RST -> CANCEL; return to inbox.
4. Tap RST -> RESTART.
5. Monitor logs for UI confirmation and HAL restart request.
6. After reboot, verify identity/history/dedupe remain intact and boot count advances.
7. Repeat one incoming and one outgoing LXMF test.

## Crown scope

This patch does not repair or diagnose the crown electrical/input path. That is intentionally separate so an input-driver change cannot contaminate the persistence/network regression test.
