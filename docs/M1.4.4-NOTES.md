# M1.4.4 Notes — exact microStore 0.1.7 no-op adapter contract

## Scope

M1.4.4 is a narrow correction to the filesystem compatibility layer introduced during the M1.4 microReticulum 0.5.0 security rebase. Radio, partition, storage-record, LXMF routing, and UI behavior are intentionally frozen.

## Root cause of the M1.4.3 compile failure

The exact `microStore 0.1.7` header `microStore/Adapters/NoopFileSystem.h` wraps the adapter definition in:

```cpp
#if defined(USTORE_USE_NOOPFS)
...
namespace microStore { namespace Adapters {
class NoopFileSystem : public microStore::FileSystem { ... };
}}
#endif
```

M1.4.0/M1.4.2-era builds did not define `USTORE_USE_NOOPFS`, so including this header produced no `microStore::Adapters` declaration. We incorrectly interpreted that compiler symptom as proof that the namespace was not part of 0.1.7 and M1.4.3 then guessed a nonexistent root-level `microStore::NoopFileSystem()` factory.

## Correct API contract

M1.4.4 defines `USTORE_USE_NOOPFS=1` and uses:

```cpp
microStore::Adapters::NoopFileSystem
```

as the concrete adapter class. A `std::is_base_of` assertion binds the shim to the expected `microStore::FileSystem` inheritance relationship.

## Lifecycle detail

`NoopFileSystem::init()` intentionally returns `false` in microStore 0.1.7. That return value means there is no backing filesystem to initialise; it must not be treated as a failed adapter construction. M1.4.4 checks that the adapter object is valid, registers it with `RNS::Utilities::OS`, and then starts Reticulum.

microReticulum 0.5.0 calls `OS::storage_size()` and `OS::storage_available()` unconditionally at the beginning of `Reticulum::start()`, which is why a registered filesystem abstraction remains required even while `RNS_USE_FS` and `RNS_USE_PROVISIONING` are disabled.
