# ReticulumWatch v1.3.0-build2

## Purpose
Navigation correctness patch for v1.3 peer intelligence.

## Fixes
- Peer cards now resolve the LVGL callback object with `lv_event_get_current_target_obj()` and explicitly enter Peer Details.
- Contact cards use a dedicated callback and explicitly enter Peer Details.
- Peer Details remembers whether it was entered from Peers or Contacts, so Back returns to the correct list.
- CHAT from Peer Details remembers its origin, so Back from the conversation returns to Peer Details instead of Messages.
- NAME opened from Peer Details returns to Peer Details after save/back; NAME opened from a normal conversation still returns to that conversation.
- Notification-opened threads return to the watch face.
- STAR wording on Peer Details is renamed to PIN/PIN* to clarify that this is a local priority flag, not a Reticulum networking feature.

## Favorite / Pin semantics
The persisted `favorite` flag is local-only. It:
1. sorts the peer above non-favorites;
2. implicitly saves the peer as a contact;
3. makes the peer preferentially resistant to bounded peer-cache eviction;
4. persists across reboot.

It does **not** affect Reticulum routing, announces, link establishment, RF priority, retries, or delivery semantics.

## Test
1. Menu -> Peers -> tap a card. Expect Peer Details, not chat.
2. Back from Peer Details. Expect Peers.
3. Peer Details -> CHAT -> Back. Expect Peer Details.
4. Menu -> Contacts -> tap a card. Expect Peer Details.
5. Back from Peer Details. Expect Contacts.
6. Peer Details -> CHAT -> Back. Expect Peer Details.
7. Toggle PIN and verify the peer rises above non-pinned peers/contacts; reboot and verify it remains pinned.
