# ReticulumWatch M2.6.0 — Integrated Messenger

## Scope

M2.6.0 consolidates the remaining M2 messenger UX work into one milestone build instead of serial minor releases. M2.1.0 is the hardware-accepted baseline.

### Features

1. Conversation threads by peer destination.
2. Persistent unread/read state.
3. Announce-discovered `lxmf.delivery` peers.
4. Persistent friendly names and favorites.
5. Manual destination entry and new-conversation flow.
6. Full composer and quick replies.
7. Opportunistic PacketReceipt proof tracking.
8. Bounded retries (maximum three physical attempts).
9. Bounded route recovery window.
10. Separate delivery/peer sidecars; no LMX journal-format migration.

## Delivery-state semantics

- `SUBMITTED`: accepted for local transmission; remote delivery is not yet proven.
- `RETRYING`: a proof timed out or a route/send attempt needs recovery.
- `DELIVERED`: cryptographic Reticulum packet proof was received.
- `FAILED`: retry/path-recovery bounds were exhausted.

Direct Link replies remain `SUBMITTED` where the pinned microReticulum Link path cannot provide a trustworthy PacketReceipt proof. The UI must not promote local TX success to delivery.

## Diagnostics

```text
[m2:peer]      announce discovery and peer cache
[m2:contact]   contact/favorite persistence
[m2:thread]    thread rebuild/index/read transitions
[m2:tx]        logical message and physical TX attempts
[m2:receipt]   proof/delivery events and RTT
[m2:retry]     timeouts, path recovery, retry/failure
[m2:store]     sidecar/journal persistence
[m2:ui]        navigation, composer and actions
```

## Hardware acceptance

1. Boot without erasing storage; verify the same identity/destination is restored.
2. Verify prior M2.1 messages are visible in conversation threads.
3. Trigger/receive an announce; verify the peer appears under **PEERS**.
4. Save a friendly name, favorite it, reboot, and verify both persist.
5. Receive a new LXMF message; verify the correct thread and unread indicator update.
6. Open the thread; verify unread clears and stays cleared after reboot.
7. Send a reply over an active Link; verify it transmits and stays honestly `SUBMITTED` unless a trustworthy proof path exists.
8. Send opportunistically to a known peer; verify `SUBMITTED -> DELIVERED` when proof arrives.
9. Exercise a failed/unreachable destination and capture `[m2:retry]` / `[m2:receipt]` output; verify retries stop.
10. Test manual destination entry and both quick replies.

## Release validation

The supplied static preflight protects the known-good M2.1 networking hashes, checks metadata/journal invariants, checks bounded retries, and runs the partition validator. A real PlatformIO cross-build and hardware acceptance are still required.
