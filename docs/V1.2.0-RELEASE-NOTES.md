# ReticulumWatch v1.2.0 — Messaging Send-State UX

## What changed

v1.2.0 adds the first post-stable messaging interaction refinement. Text-message sends now enter a visible modal state before the existing LXMF submission path runs.

### New user-visible behavior

When sending text from any supported text-send entry point, the watch displays:

```text
Sending message...
Submitting to Reticulum
```

The overlay is modal: the underlying composer/thread/notification controls cannot be tapped while the send is being submitted.

The following entry points use the same path:

- composer SEND;
- quick reply 1 from a conversation;
- quick reply 2 from a conversation;
- quick replies from an incoming-message notification.

### Submission semantics

The popup describes **local Reticulum submission**, not remote delivery. The existing conservative delivery semantics remain unchanged:

- `SUBMITTED` means the watch handed the message to the accepted Reticulum path;
- path-request/queued sends may also be accepted locally before a peer is reachable;
- the UI does not claim `DELIVERED` without the existing proof-backed evidence;
- active-Link sends remain conservative where the pinned microReticulum proof status cannot be safely asserted.

### Deferred UI handoff

Text content and destination are copied into a bounded pending-send buffer. The send is deferred by a short UI interval so LVGL has a chance to paint the modal before the existing synchronous send path begins. No Reticulum/LXMF/radio code was modified for this feature.

## What did NOT change

- SX1262 radio profile/framing;
- microReticulum startup or endpoint mode;
- LXMF packet construction/signing;
- persistent message journal format;
- identity;
- Codec2/audio/PTT behavior;
- crown/lift wake behavior;
- v1.1.0 clock size and optical centering.
