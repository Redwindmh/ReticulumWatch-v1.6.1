# M1.3.0 — Independent opportunistic outbound LXMF

## Major milestone

**M1 — LXMF Messaging Core**

Sub-milestone: **M1.3 — Outgoing LXMF**.

## Acceptance criterion

A human-readable message must be sent from the watch to an external LXMF client even when that peer has **not first opened a fresh incoming Link to the watch in the current boot/session**.

For M1.3.0 the destination is selected from existing message history. Contacts/address-entry/new-conversation UX remains M2 work.

## Already proven before this change

M1.2.7 preserves and hardware-validates:

- stable permanent identity;
- Reticulum/SX1262 RX and TX;
- incoming Links;
- inbound LXMF decode/persistence;
- signed Link replies;
- LMX3 `RECEIVED`/`SUBMITTED` records;
- reboot restoration;
- durable dedupe;
- large-key composer.

## Smallest change

Retain the working Link sender and add a second outbound route:

1. active matching Link -> existing Link send;
2. otherwise, if Reticulum already knows the path and identity -> opportunistic SINGLE send;
3. otherwise request the path, retain one message in RAM, and send when path+identity resolve.

No contacts database, discovered-peer UI, message threading, transport mode, or RNS persistence is added here.

## Known-good behavior that must remain untouched

- RadioService and RNode framing;
- WatchLoRaInterface;
- ReticulumService startup and application identity;
- LMX3 storage format/CRC/retention/dedupe;
- M1.2.7 keyboard geometry;
- reboot control.

## Opportunistic LXMF construction

Signed material:

```text
dest16 + source16 + payload
message_id = SHA256(signed-material-before-message-id)
signature = Ed25519(dest16 + source16 + payload + message_id)
```

Link plaintext:

```text
dest16 + source16 + signature64 + payload
```

Opportunistic SINGLE plaintext before Reticulum encryption:

```text
source16 + signature64 + payload
```

The outer SINGLE destination carries `dest16` for opportunistic delivery.

## Path-request lifecycle

- one pending outbound message maximum;
- RAM only;
- 30-second timeout;
- 250-ms route/identity poll in normal loop context;
- if a matching incoming Link becomes active during the wait, use it immediately;
- otherwise send opportunistically once both path and recalled identity are available.

## Deferred work

- arbitrary address entry / new conversations;
- persistent outbox and retry after reboot;
- multiple queued sends;
- delivery receipt state transitions;
- contact/discovered-peer UI;
- signature hardening / late LINKIDENTIFY verification.
