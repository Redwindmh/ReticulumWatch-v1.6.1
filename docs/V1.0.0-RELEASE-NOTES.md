# ReticulumWatch v1.0.0 — First Stable Release

## What changed from M13

v1.0.0 is the stable graduation of the hardware-accepted M13 release candidate. It intentionally does **not** introduce a new protocol, radio, storage, audio, power, or UI feature.

Changes in this artifact are release-facing:

- firmware version is now `1.0.0`;
- milestone/build macro moves from the internal M13 line to stable-release marker `100`;
- stable-release documentation and a concise hardware test guide are added;
- the M13 feature freeze is preserved;
- the frozen M6-build3 Reticulum/LXMF/radio boundary remains untouched;
- M12-build4 crown and interrupt-driven lift-to-wake behavior is preserved unchanged.

## Features present in v1.0.0

The first stable release includes the integrated feature set proven across M0–M13:

- standalone LoRa Reticulum endpoint on LilyGo T-Watch S3;
- Reticulum announces, discovered peers and incoming Links;
- LXMF send/receive, conversations, unread state, contacts and quick replies;
- persistent identity, message history, delivery/read metadata and corruption handling;
- watch-native dark UI, clock/date and message alerts;
- connected standby with Reticulum RX active while the display is off;
- crown display toggle;
- optional persistent Lift to Wake using BMA423 hardware feature interrupts;
- sleeping touch disabled as a wake source;
- optional Wi-Fi/TCP Reticulum interface support;
- public identity/address QR exchange and manual destination import;
- local audio capture/playback and Codec2 voice-message support;
- runtime supervisor and resource telemetry;
- USB recovery/backup console and confirmation-gated destructive recovery.

## Known non-blocking limitations

- Lift-to-wake sensitivity is governed by the accepted BMA423 TILT/WAKEUP feature path. No speculative dependency patch is included.
- Sideband cross-client Codec2/audio interoperability may still require additional ecosystem testing.
- Transport Node functionality remains experimental/locked rather than being advertised as a stable battery-wearable feature.

## Release rule

Any future behavioral feature should begin a new post-1.0 development milestone. Stable maintenance builds should remain narrowly scoped to regressions, security fixes, compatibility fixes and evidence-backed hardware corrections.
