# M1.2.3 — durable history/index recovery

## Major milestone

M1 — LXMF Messaging Core, specifically M1.2 persistent inbox/history reliability.

## Acceptance criterion for this patch

A firmware reboot or a damaged derived index must not cause the watch to forget existing chronological LXMF history or overwrite an existing history sequence. A previously persisted LXMF message ID must remain recognizable as already stored after reboot.

## Why this patch exists

M1.2.2 kept a 32-bit `/lxmf/message_count.bin` value and only remembered the latest message ID in RAM. Two reliability holes followed:

1. if the count file became truncated/stale/corrupt, resetting it to zero could allow a later save to reuse an existing sequence filename;
2. duplicate suppression only knew the latest ID in RAM, so an older LXMF retry or a duplicate delivered after reboot could be persisted again.

Those are storage-layer problems. M1.2.3 therefore does not alter SX1262, RNode framing, Reticulum destination behavior, Link handling, LXMF wire construction, or the working M1.2.2 composer layout.

## Changes

- `/lxmf/inbox/*.lxm` files are treated as the authoritative chronological journal.
- At boot, the highest valid sequence-shaped filename is discovered and `/lxmf/message_count.bin` is repaired if necessary.
- `/lxmf/metadata` is created.
- A `<64-hex-message-id>.idx` marker is maintained for each readable message ID.
- Existing LMX1/LMX2 history is backfilled into the marker index on boot.
- Missing marker lookup falls back to scanning readable history if the metadata rebuild was incomplete.
- `LxmfService` checks the durable storage index in addition to its in-RAM last-ID fast path.
- Duplicate receives are logged and ignored before a second history record is written.
- Invalid LMX1/LMX2 records are skipped rather than treated as valid.
- `loadLatestLxmfMessage()` walks backward until it finds a readable record.
- `/lxmf/outbox` is created now to match the master storage layout, but the existing single chronological LMX1/LMX2 history remains in `/lxmf/inbox` for backward compatibility.

## Expected boot diagnostics

On an existing M1.2.2 partition, first M1.2.3 boot should include lines similar to:

```text
[storage] LXMF history audit: readable=... unreadable=... id_markers_added=...
[lxmf] restored latest history message #...
[lxmf] durable dedupe lookup for latest message: PASS
```

A second boot should normally report `id_markers_added=0` and still show `PASS`.

## Deliberately not included

- bounded retention/deletion policy;
- LMX3/CRC record migration;
- opportunistic outbound/new-conversation UX;
- contact/peer discovery;
- security dependency rebase;
- delivered/read state.

Those remain separate changes so the proven M1.2.2 network path stays isolated from this storage hardening patch.

## Verification status

Source-audited and packaged. Not build-verified in the generation environment because PlatformIO is not installed there. Hardware acceptance remains the user's PlatformIO build/flash/reboot test.
